# mhszed-sql · 审计思路与工具流程（2026-10-22 版）

> 本文描述**当前实际生效**的审计方法论与工具流水线，覆盖 2026-10-13 MVP 之后
> 在真实靶场（真实靶场与本地 sqli-labs）上迭代出的关键设计。

## 一、核心审计原则

1. **证据优先，不靠猜**
   - AI 研判前必须先用真实请求采探针证据；没有证据就给高置信，视为缺陷。
   - 报告里的每个结论都要能追溯到请求/响应/Payload/命令。

2. **模仿语境，不背模板**
   - Payload 先生成“这个接口能用的形态”，不是套一套万能 payload。
   - 先判断引号/括号语境，再决定闭合方式与注释；sqlmap 已确认的 payload 优先。

3. **默认不信任单次命中**
   - 误报样本库负样本压制；
   - 每条 payload 必须带预期判据；
   - 原则上 ≥2 个向量一致才产出；
   - 强证据（DBMS 专属报错、UNION 版本回显）允许单向量；
   - 最终仍进人工复核。

4. **先保护目标，再追求结果**
   - 授权范围是硬约束；
   - 限速、熔断、写接口保护、总预算；
   - 目标连续连接失败立即停，不换引擎继续打；
   - 实战默认 `goal=schema`，拿到库名即停。

5. **任何异常先查证据链路**
   - 先问“工具拿到证据了吗 / 判据有没有把结论吃掉 / 参数有没有在适配层被吞”，
     最后才怀疑模型能力。

6. **只信权威来源**
   - 当前库/schema：sqlmap `--current-db`（PG 下为 schema，必须区分 database）；
   - 真实数据库名：`SELECT current_database()`；
   - 盲注轻量提取默认关闭，避免 `library→lihrary`、`challenges→challdnges` 类误读；
   - 标量查询强制 `--fresh-queries`，不复用错误缓存。

## 二、工具总流程

```
目标 URL + 授权范围
  │
  ├─ 0. 授权校验（不在 auth_scopes → 403，零探测请求）
  │
  ├─ 1. 接口采集
  │     ├─ 静态爬虫：HTML/JS/表单/带参链接
  │     ├─ 常见参数名探测（无表单 GET 页也覆盖）
  │     └─ Burp 推送（/api/burp/push，幂等去重）
  │
  ├─ 2. 归一建模
  │     ├─ 指纹去重（method + 路径模板 + 参数结构）
  │     ├─ 读写分类
  │     └─ 业务会话链还原（referer / token 指纹 / 时间聚类）
  │
  ├─ 3. WAF 画像（产品 + 行为 + 置信度 + 建议绕过）
  │
  ├─ 4. AI 分级研判（先探针采证，再用证据纠偏打分）
  │     ├─ ≥0.9 auto_pass
  │     ├─ 0.6~0.9 manual_review
  │     └─ <0.6 suspicious
  │
  ├─ 5. 人工复核（确认 / 误报 / 调分；确认后恢复扫描）
  │
  ├─ 6. 流水线探测
  │     ├─ AI 探针优先（确认则跳过 sqlmap）
  │     ├─ sqlmap 初筛（分类：确认 / 无 / 拦截 / 存疑 / 超时 / 不可达）
  │     ├─ 被拦截/存疑 → AI Payload 精细化
  │     └─ 结果分类器路由，最多 N 轮（默认 2）
  │
  ├─ 7. 证据归档 + 漏洞产出（默认 pending_review）
  │
  ├─ 8. 深入利用（goal=schema / flag 每次必选）
  │     ├─ schema：拿到当前库/schema 即停，不枚举表、不取数
  │     └─ flag：按预算枚举表/取样，仍受总预算与目标保护限制
  │
  └─ 9. 报告导出 + 知识回流（成功 Payload / 误报负样本）
```

## 三、阶段详解

### 0. 授权与安全前置
- 目标 host 必须命中 `auth_scopes`（精确域名 / 通配符 / IP，支持过期时间）。
- 未授权目标：403，任务停在 created，不产生任何探测请求，审计留痕。
- 所有出站请求统一走 SafeHttpClient（限速 / 审计 / 授权校验）。
- sqlmap 子进程与部分深挖脚本不受 SafeHttpClient 管辖，依赖 runner 的
  `--threads 1 --delay 0.5`、同 host 串行与总预算约束。

### 1. 接口采集
- 静态爬虫：解析 HTML/JS，登记表单、带参链接、JS 中出现的 API 路径。
- **参数猜测**：对没有 query 参数的 GET 页面尝试常见参数名
  （id/q/sort/order/search/keyword/name/page/category/user/uid/type），
  状态码或长度变化超过阈值才登记。
  - 关键修复：POST 表单不再抑制 GET 参数猜测。
    （sqli-labs Less-59 只有 POST 表单，真正注入在 `?id=`，旧逻辑会漏测。）
- Burp 推送：与爬虫结果合并，按“请求指纹 + task_id”幂等去重。
- 当前限制：404 接口仍可能被采集；AI 判断页会明确标注“接口 404”，
  但尚未在采集阶段直接过滤。

### 2. 归一建模
- 接口指纹 = method + 路径模板（数字/UUID 替换为 `{id}`）+ 参数结构。
- 读写分类：GET/HEAD → read；POST/PUT/DELETE/PATCH → write；再按语义修正。
- 会话链三级还原：
  - Referer 链（置信度约 0.95）；
  - 会话凭证 SHA256 指纹聚类（约 0.8）；
  - 时间序 + 路径语义聚类（约 0.5，标记 `inferred=true`）。
- 推断链路只用于展示与误报辅助，不作为写接口探测的放行依据。

### 3. WAF 画像
- 无害探针 + 响应特征比对，输出结构化画像：产品、置信度、
  拦截特征（状态码/页面指纹/响应头/关键词）、建议绕过策略。
- 新增“静默过滤”识别：裸引号有差异、含空格 payload 零变化 → 判存在 WAF。
- 产品覆盖：ModSecurity / 阿里云盾 / 腾讯云 WAF / 安全狗 / D 盾 / 宝塔 /
  雷池 / Cloudflare / F5 / 其他 / 未知。

### 4. AI 分级研判（核心）
**探针档位（7 档）**
```
baseline → 1' → 1'' → 1') → 1") → bypass_true → bypass_false
```
- 每个接口最多取前 3 个参数；请求间隔 0.3s。
- 采集证据：
  - SQL 报错特征（unrecognized token / sql syntax / sqlite / 查询异常 等）；
  - 引号奇偶差异；
  - 绕过形态是否揭示被普通引号吃掉的报错（bypass_reveal）；
  - true/false 绕过档响应差异（bypass_diff）。

**证据纠偏**
- 探针见 SQL 报错或强绕过证据 → `risk≥85 / conf≥0.95` 的 floor；
  floor 必须高于 auto_pass 阈值 0.9。
- 命中误报样本库 → 压制到 `risk≤30 / conf≤0.5`。
- 探针全部失败（连接拒绝/重置 = 目标不可达）→ `conf≤0.5`，
  防止“确信无漏洞”型高置信误触 auto_pass。
- 无 AI Key → 规则引擎降级，全流程仍可跑通。

**路由**
- `conf≥0.9`：auto_pass → 进入探测队列；
- `0.6≤conf<0.9`：manual_review → 人工复核；
- `<0.6`：suspicious → 交人工/存疑深测，不直接猛扫。

**Payload 生成**
- prompt 注入探针证据、推断 DBMS、知识库成功样本、历史尝试、sqlmap 摘要。
- 要求先推断引号/括号语境，再生成 payload；布尔真假必须成对；
  按 DBMS 分流（SQLite / PostgreSQL / MySQL）。
- 无 AI 时降级内置模板（含引号型、数字型、SQLite 专用、WAF 绕过形态）。

### 5. 人工复核
- 队列动作：确认 / 误报 / 调整分数。
- 确认后自动恢复扫描（`/api/scan/resume`），仅把已确认的接口纳入探测。
- 误报会回流负样本库，下一次研判前置压制。

### 6. 流水线探测
- **AI 探针优先**：轻量、带绕过，确认后跳过 sqlmap（避免 sqlmap 把目标打挂）。
- **sqlmap 初筛**：
  - 逐参数测试，兄弟参数置空；
  - 只带证据驱动的 `--dbms`；
  - 结果分类：vuln_confirmed / no_vuln / waf_blocked / inconclusive /
    timeout / unreachable / error。
- **结果分类器**：被拦截、存疑、超时接口交给 AI 精细化；
  同一接口最多往返 2 轮。
- **假成功防治**：
  - `[CRITICAL]` 等致命标记 + 零产出 → error；
  - exploit_ok 不能只凭“有输出”，也不能把 session 恢复时打印的
    `current database:` 当战果。
- **目标不可达保护**：
  - sqlmap 连续 4 次连接失败 → 主动杀进程，返回 `unreachable`；
  - 扫描/复核恢复流程遇到 unreachable → 整任务 terminated；
  - 深挖遇到 unreachable → 立即停止。

### 7. 漏洞与证据
- 漏洞默认 `pending_review`，人工确认后才转 `confirmed`。
- 证据链只追加不修改：
  request / response / payload / waf_info / chain_info / console_log / deep_exploit。
- 每条证据带 seq 与 SHA-256。
- 超时升级为 `vuln_confirmed` 时，从 findings 的 parameters 补确认 Payload，
  不让证据在超时分支丢失。

### 8. 深入利用
**目标必须每次显式选择：`goal=schema` 或 `goal=flag`。**

- `goal=schema`：
  - 拿到当前库/schema 即停，不枚举表、不取样；
  - 只信 sqlmap `--current-db`（权威）；
  - PostgreSQL 的 `--current-db` 返回 schema（如 public），
    真实数据库名单独用 `SELECT current_database()` 获取；
  - 不采信 UNION 剧本/AI 盲注在报错页上解析出的库表。
- `goal=flag`：
  - 才允许继续枚举表、取样（dump 最多 5 行）；
  - 仍受总预算与目标保护约束。

**执行方式**
- mode=ai / enum / dump；
- 每步动作：current_db → db_name（PG）→ tables → dump；
- `--fresh-queries` 强制不复用错误缓存；
- `union_extract` 只对 SQLite 启用（未知 DBMS 不再放行）；
- 轻量盲注提取默认关闭（`deep_use_blind_extract=false`）；
- 总预算 `deep_total_budget_s`（默认 900s，可配），每步超时受剩余预算约束；
- 最多 4 步 sqlmap，避免死循环；
- 前后缀优先用已确认 payload 反推，AI 只在无实证时兜底；
  AI 技法只能放宽不能收窄；PG 纯盲注固定 BT。

**证据展示**
- 影响证明：数据库类型、当前库/schema、表、样本/flag；
- 提取方式：优先展示 sqlmap 实际参数（如 `sqlmap --dbms MySQL --current-db --fresh-queries`）；
- 表只采信 `impact_tables / dump_result`，出现 PHP 报错词整份丢弃；
- 确认 Payload 优先展示真正起作用的 WAF 绕过形态，`sqlite_master` 探测词降权；
- 不展示“单一完整 URL 的取库 payload”：`--current-db` 是逐字符布尔请求，
  不存在一条固定 URL；强行拼接会误导。

### 9. 报告与知识回流
- 报告字段：测试 URL、请求方法、参数、DBMS、确认 Payload、
  影响证明、sqlmap 提取命令、关键判定行、结论、加固建议。
- 类型/严重度/状态中文化。
- 证据选择：同阶段取最新，避免旧的 `challdnges` 压过修复后的 `challenges`。
- 知识回流：
  - 确认漏洞 → 成功 Payload 入知识库；
  - 人工标误报 → 接口指纹+响应指纹入负样本库；
  - 下次研判前置检索负样本。

## 四、目标保护与运行参数（实战建议）

| 项 | 默认 / 建议 |
|---|---|
| 授权范围 | 必须先配置，未命中直接 403 |
| rate_limit_qps | 1.0（限流靶机的甜点，勿提速） |
| WAF 熔断 | 错误率 0.3 / 拦截率 0.5 / 窗口 60s / 冷却 300s |
| sqlmap | `--threads 1 --delay 0.5`，同 host 串行 |
| 连续连接失败 | 4 次 → 主动终止，任务/深挖停止 |
| 深挖总预算 | 默认 900s，可配 300~600s 更稳 |
| 深挖步数 | 最多 4 步 |
| goal | 实战默认 `schema`；flag 只用于靶场 |
| dump | 仅 `goal=flag` 且 mode=dump，最多 5 行 |
| 并发 | 同一 host 不要多任务并发；采集阶段同理 |

## 五、当前能力边界与已知问题

1. **二次注入未覆盖**
   - Less-24 这类“注册存 payload → 另一页面触发”的链路不建模；
   - 目前只做单请求参数 → 响应的即时检测。
2. **404 接口**
   - 采集阶段仍可能登记 404 接口；AI 判断页会标注“接口 404”，
     但尚未在采集阶段过滤。
3. **静态爬虫的无表单 GET 参数**
   - 已用常见参数名猜测补了一部分；非常见参数名仍可能漏。
4. **boolean_blind.py**
   - 使用裸 httpx，绕过 SafeHttpClient（无限速/审计/授权校验），
     是产品自身管控缺口。
5. **WAF 反推**
   - `waf_learn` 目前只识别 space 变换；kw_once 逻辑已写但现场未触发；
     计划升级为通用 diff 引擎。
6. **深挖 dump 模式**
   - 长期只验证 enum/current_db，dump 未做真机回归。
7. **请求级 URL 展示**
   - 不展示 sqlmap 逐字符请求的完整 URL；需要时用 `-v 3` 采 `[PAYLOAD]`，
     但会增加输出与解析风险。

## 六、关键判据速查

- AI 路由：0.9 / 0.6。
- 探针报错 floor：risk ≥85，conf ≥0.95。
- 探针全失败：conf ≤0.5。
- 布尔判据：true 还原基线、false 与基线不同；
  或时间差 ≥1s 且 ≥2 倍（双向）。
- 报错判据：命中关键词且基线不含该关键词。
- UNION 报错判据：只认列数不匹配类（MySQL 1222 / SQLite different number of
  result columns / PG same number of columns / SQL Server equal number of expressions）。
- 强证据单向量可确认：DBMS 专属报错、UNION 版本回显；
  其余原则上 ≥2 向量，否则 inconclusive。
- 证据链排序：flag > 可信库表 > 最新 impact/current_db/tables/stop；
  `stop/result` 不再携带历史脏表名。

## 八、WAF 与应用层过滤的分层（2026-10-23）

两类目标必须分开处理，不能把"靶场招式"当成"真实 WAF 绕过"：

| | 应用层过滤（app_filter） | 真实 WAF 产品 |
|---|---|---|
| 典型实现 | `str_ireplace(['or','and'], '', $v)` 单次替换 | 签名库/正则/语义分析（Cloudflare、安全狗、雷池、ModSecurity…） |
| 有效手法 | 双写（`OORR`/`AANNDD`）、注释切分、等价运算符、空格替代 | 解析差异、协议与架构层：Host/XFF、Content-Type/multipart、分块传输、HPP、请求走私、真实 IP |
| 判据 | 真/假对照出现差异 | 产品指纹 + 拦截行为 |

**约束**

- `OORR`/`AANNDD` **不是**真实 WAF 的通用绕过；只作为 `app_filter_single_pass`
  技术条目存放在 `kb_insights`，不进入通用内置 payload 池。
- sqlmap 的 `orand` tamper 只在已确认 payload 本身带 `OORR/AANNDD` 时挂载。
- 真实 WAF 的对抗应走架构层与解析差异，并保持单 host 低请求节奏；
  拦截率上升立即停止（熔断/保护目标）。

**知识库**

- `kb_insights` 条目带 `tags`：`app_filter_single_pass` / `not_for_real_waf`，
  检索时按标签区分；验证成功才回流计数。
